# workbuddy-wild 代码审计报告

**审计日期**：2026-10-08
**审计依据**：`docs/DEVELOPMENT.md`（v0.8.0 重写版）中的「硬性约束 / 已实测排除 / 踩坑史 / 模块实现规格」逐条对照源码
**审计方法**：文档断言 → 源码验证；`go vet` + `go test ./internal/...` 全绿（说明以下问题**测试覆盖不到**）
**结论**：**发现 3 个真实缺陷**（1 个用户可见 + 2 个死代码/失效机制），均为**文档已澄清但代码未同步**类问题。

## 缺陷 1（用户可见）：9074 的中文提示永远不会显示，用户看到英文技术错误

**位置**：`internal/scheduler/scheduler.go:501-507`（分支）与 `:468`（实际赋值）

```go
// 468 行：先把原始错误写进用户提示
r.Msg = shortErr(checkinErr)          // → "checkin 9074 (transient throttle): 当前参与用户太多，请稍后再试"

// 501-507 行：本想覆盖成中文可操作提示，但分支永不成立
} else if isRateLimited(checkinErr) {
    // 上游 9074：设备号未被认作已注册设备。**不是限流**，
    // 重试永远不会成功（v0.5.7 已实测确认），因此不安排重试，
    r.Msg = "签到被拒：设备号未注册，请重新添加该账号"   // ← 永远走不到
```

**根因（三重）**：
1. `isRateLimited()` 的唯一实现是 `traework.(*ErrCheckinRateLimited).IsRateLimited()`，而它在 **v0.6.9 已改成返回 `false`**（`traework/client.go:179`，理由：重试已在 `claimWithRotatedDevice` 内部完成，不想再排调度器重试）。
2. 于是 `isRateLimited(checkinErr)` 对 9074 **恒为 false** → 501-507 整个分支是**死代码**。
3. 该分支的注释与文案仍停留在 v0.5.7 的**已被推翻的定性**（"设备号未注册、重试永远不会成功"），而文档 §4.4 / §6.5 / 附录 B.2 已明确：**9074 = 瞬时限流、可重试、内部换号 ≤8 次**。

**影响**：用户在「8 次换号仍被限流」时会看到英文技术文案 `checkin 9074 (transient throttle): ...`，而不是设计好的中文提示。

**建议修复**：
- 方案 A（推荐）：把判定从"接口探测"改为"类型断言"，即直接 `errors.As(err, &*traework.ErrCheckinRateLimited)`（需要暴露一个 `errors.Is` 哨兵或 `IsCheckinRateLimited(err)` 辅助函数——**后者已存在**，见 `traework/client.go:182`）。
- 方案 B：保留分支但改正文案与注释，例如："签到触发上游限流，已自动换号重试 8 次未成功，请稍后手动重试"。
- **同时必须**修正 :503 与 :506 的注释（删掉"重试永远不会成功"的结论）。

## 缺陷 2（死机制）：`CheckinResult.Retryable` 全仓库无赋值点，延迟重试队列永不触发

**位置**：`internal/scheduler/scheduler.go:338`、`:373-374`

```go
// 374: 字段定义
Retryable bool `json:"retryable,omitempty"`

// 338: 唯一的消费点
} else if r.Retryable {                       // ← 永远为 false
    if at, ok := s.markRetryable(uid, now); ok { ... }
}
```

**验证**：全仓库检索 `Retryable` 的赋值（`Retryable: true` / `.Retryable =`），**零命中**（仅 `retry_test.go:10` 注释提到"原实现仅在 CheckinResult 上设 Retryable=true，但没有任何代码…"）。

**影响**：
- `markRetryable()` / `retryState` / 调度器的"延迟重试队列"**整体失活**（`RunRetryPass` 里 no-op）。
- 文档 §6.5 所述"调度器的延迟重试队列只用于跨小时的补签场景"——**该机制当前不存在**。

**建议修复**：
- 若确需该机制：在 `checkinOne` 里对"可重试的瞬时错误"（如上游 5xx、`ErrServer`、`ErrSoftRate`）显式 `r.Retryable = true`。
- 若已废弃：删除 `Retryable` 字段、`markRetryable`、`retryState` 与 `RunRetryPass` 的对应分支，避免"看起来有重试其实没有"的误导（这点尤其重要，因为它是**可靠性相关**的错觉）。

## 缺陷 3（假阳性测试）：9074 的测试并未真正覆盖 `IsRateLimited` 路径

**位置**：`internal/scheduler/checkin_classify_test.go:87-110`

```go
checkinErr: errors.New("checkin 9074 (device not registered): 当前参与用户太多，请稍后再试"),
...
if r.Retryable { t.Fatal("9074 是设备未注册，重试无效，不得标记 Retryable") }
```

**问题**：用裸 `errors.New` 模拟，**不实现 `rateLimited` 接口**，因此 `isRateLimited()` 走 `return false` 的兜底，而**不是**走 `ErrCheckinRateLimited.IsRateLimited()`。
测试"通过"的原因是**分支根本没进**，不是语义正确 → **假阳性**。

**影响**：该测试给了"9074 行为已被验证"的错觉，掩盖了缺陷 1。

**建议修复**：用真实的 `*traework.ErrCheckinRateLimited{}` 构造错误（而非 `errors.New`），并断言最终 `r.Msg` 是**中文可操作提示**而非英文 `Error()` 输出。

## 附 2：一个**非代码**问题（文档/代码命名偏差）

- 文档附录 A.1 把 `CheckinAlreadyClaimedCode` / `CheckinBadParamsCode` 与其它常量并列列在 `constants.go`，但 **`CheckinRateLimitCode`(9074) 实际定义在 `client.go:154`**，另两个在 `constants.go:57/60`。重写时按文档只会去 `constants.go` 找 9074 → 找不到。

## 优先修复顺序

1. **缺陷 1**（用户可见 + 注释错误定型）—— 影响实际使用体验，且注释会误导后续维护。
2. **缺陷 2**（可靠性错觉）—— "看起来有重试其实没有"是运维隐患；若确无需要应删除。
3. **缺陷 3**（假阳性测试）—— 修复后会**立即暴露**缺陷 1，属于防回归的必要投入。
