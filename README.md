# WorkBuddy Wild

**WorkBuddy/CodeBuddy + TraeWork 账号的 OpenAI 兼容代理 + 自动签到 Windows 托盘工具。**

双平台支持：聚合多个 WorkBuddy 和/或 TraeWork 账号，提供统一 OpenAI 兼容 API。
支持模型前缀区分（`workbuddy/<model>`、`traework/<model>`），自动路由到对应上游。

面向普通用户：**下载即用**，一个 exe 搞定账号登录、自动签到、积分查看、模型路由，为你的 AI 客户端（pi、Claude Code、Cursor 等）提供 OpenAI 兼容接口。

> 本项目源于两个原始项目，在其基础上重做为 Windows 双平台托盘应用：
> - [Sliverkiss/workbuddy2api](https://github.com/Sliverkiss/workbuddy2api) — WorkBuddy/CodeBuddy 上游
> - [Sliverkiss/traework2api](https://github.com/Sliverkiss/traework2api) — TraeWork SOLO 上游
> 
> 开发者/高级配置见 [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)。

### v0.7.0（2026-10-02）
- **模型名支持备注** —— 可在名称后随意追加说明，调用上游前自动剥离
  - **用户需求**：「能不能让模型名支持备注，如 workbuddy/deepseek-v4-flash（倍率0.11x），
    括号里可以随意填备注内容」
  - **用法**：在模型名后直接跟括号备注即可，内容随意：
    ```
    workbuddy/deepseek-v4-flash（倍率0.11x）
    workbuddy/glm-5.2【便宜】
    traework/glm-5.2(rate low)
    workbuddy/kimi-k2.7「备用」
    ```
    以上都会被正确路由到 `deepseek-v4-flash` / `glm-5.2` / `kimi-k2.7`。
  - **支持的包裹符**（成对，任意一种）：
    | 起始 | 结束 | 场景 |
    |---|---|---|
    | `（` | `）` | 全角圆括号（中文输入法默认） |
    | `(` | `)` | 半角圆括号 |
    | `【` | `】` | 全角方括号 |
    | `[` | `]` | 半角方括号 |
    | `「` | `」` | 全角引号 |
  - **实现**：新增 `stripModelAnnotation()`，规则是**从第一个起始符切开，
    只保留之前的部分** —— 所以多段备注（如 `glm-5.2（倍率0.11x）(备用)`）
    能一次剥净。
  - **边界处理**：
    - 无备注 → 原样返回，行为与旧版完全一致
    - 只有备注、没写模型名（如 `（倍率0.11x）`）→ 原样返回，
      交由上层报「模型名不合法」，**不会**静默变成空串
    - 模型名本身含连字符/点/数字（如 `Doubao-Seed-2.1-Pro`）不受影响
  - **`/v1/models` 增强**：每条模型新增 `name` 与 `annotation_supported: true` 字段，
    告知客户端该 id 支持备注
  - 新增 4 个测试：
    - `TestStripModelAnnotation` —— 12 组用例覆盖各种括号与边界
    - `TestChatCompletionsStripsModelAnnotation` —— 端到端确认上游收到的 model 无备注
    - `TestChatCompletionsAnnotationForms` —— 各种括号形式端到端（含 traework 前缀）
    - `TestChatCompletionsPlainModelStillWorks` —— 无备注场景不回归

### v0.6.9（2026-10-02）
- **修复「4700 的账号今天还是 4700」** —— 9074 被误判为永久失败，导致轮换只试一次就放弃
  - **用户反馈**：「4700 的帐号今天还 4700，每日签到没增加，月初签到也没增加」
  - **查日志发现**：09:00 定时签到**确实执行了**换设备号轮换，但第 1 次随机号
    返回了 `9074「当前参与用户太多，请稍后再试」`，旧实现把它当作
    「设备号未注册、重试无用」**直接放弃** → 该账号当天没签到成功。
  - **决定性实验**（同日手工重试）：对同一账号连续用 **8 个随机设备号** claim，
    **全部返回 `code=0` 并成功 +100**（4700 → 4800）。
    → **同一操作有时成功、有时 9074，且重试就能过 ⇒ 9074 是瞬时限流，不是设备号非法。**
  - **纠正 v0.5.7 的错误定性**：9074 曾被写成"设备号未注册，重试永不成功"。
    那是基于"连续重试恒返 9074"得出的结论 —— 而今天的数据明确推翻它。
    该码文案「当前参与用户太多，请稍后再试」字面就是**暂时性**的。
  - **修复 1：轮换设备号改为最多 8 次重试**
    - 遇到 `9074`（瞬时限流）→ **继续换号重试**，不再放弃
    - 遇到 `9095`（该号今日已签）→ 同样换号重试
    - 仅在「多个设备号都试完」或「额度确认未增加」时才判定失败
    - 上限 8 次，避免无限重试
  - **修复 2：`CheckinClaim` 收到 9074 时也走换号重试**
    - 旧实现：9074 → 直接返回 `ErrCheckinRateLimited`，放弃
    - 新实现：9074 → 同样调用轮换重试，多试几个号
  - **修复 3：轮换循环的终止条件更精确**
    - 只有「`code=0` 但额度未变」才判定为"今天确实已领"并立即停止
      （此时换号是无用的，因为额度是按账号发放的）
    - 其他非 0 返回码一律继续换号
  - **重写 `CheckinRateLimitCode` / `ErrCheckinRateLimited` 的注释**，
    完整记录三次定性变更（限流 → 设备未注册 → 瞬时限流）与推翻证据
  - 新增 3 个测试：
    - `TestRotateClaimRetriesOn9074` —— 前两次 9074、第 3 次成功，必须判为入账
    - `TestRotateClaimGivesUpAfterMaxAttempts` —— 全部 9074 时才失败，且不无限重试
    - `TestRotateClaimStopsWhenNoCreditIncrease` —— 额度未变时立即停止
  - **即时效果**：账号 2222575719809915 已从 4700 增至 **4800**
  - 对照说明：账号 1554031214073648 今天流程完全正常
    （前置 `checked_in=false` → claim 成功 → 新建今日签到包）

### v0.6.7（2026-10-01）
- **对账改用服务端权威标识 `entitlement_id`**（取代启发式判定）
  - **用户追问**：「4700 这个应该还有每个月初的 500 积分呢」
    → 顺着这句去查包的原始字段，**发现了上游自带的权威标识**。
  - **重大发现**：上游给每个权益包都带了**自解释的唯一 ID**：
    | entitlement_id | 含义 |
    |---|---|
    | `checkin_20260930_2222575719809915` | 9/30 的**签到奖励** |
    | `checkin_20261001_2222575719809915` | 10/1 的**签到奖励** |
    | `monthly_bonus_202610_2222575719809915` | 2026 年 10 月的**月初奖励** |
    | `367884760578` | 固定福利包（纯数字） |

    还带 `product_extra.package_extra.package_name`（如 `"签到奖励"` / `"福利积分"`）
    与 `package_source_type`（9=签到，10=福利，0=月度）。
  - **4700 的精确构成**（服务端 ID 佐证）：
    ```
    4000  福利积分         367884760578
     500  月度奖励 2026-10  monthly_bonus_202610_...
     100  签到奖励 09-30    checkin_20260930_...
     100  签到奖励 10-01    checkin_20261001_...   ← 今天补签的
    ----
    4700
    ```
    → **你问的月初 500 确实在里面**（`monthly_bonus_202610`）。
  - **修复**：`CurrentDayGrant()` 改为直接读 `entitlement_id`：
    **前缀为 `checkin_` 且日期段等于今天** → 判定今天签到已到账。
    - 取代 v0.6.5 的「时间窗 + 金额」启发式 —— 那套能工作但脆弱：
      若签到发生在凌晨、或签到额度调整到 >300，就会再次误判
    - 现在**不再依赖任何猜测**，直接读服务端的自解释 ID
    - 缺少该字段时保守判为"未到账"，不会崩
  - 测试重写为 4 个：今天的 checkin 包被识别 / 月初包不被误算 /
    无今日包判未到账 / 缺 ID 时安全降级
  - 新增常量 `checkinIDPrefix = "checkin_"`；
    原两个启发式常量保留作兜底参考

### v0.6.6（2026-10-01）
- **修复「4600 的账号一点也没增长」** —— 根因是程序**自己跳过了 claim**
  - **用户追问**：「为什么 4600 的帐号一点也没增长？还是多帐号签到异常问题吗？」
  - **决定性实验**（绕过程序，直接打服务端）：
    | 尝试 | claim 结果 | 额度 |
    |---|---|---|
    | 账号2 + **原设备号** `4484256452647802` | `9095` | 4600（不变） |
    | 账号2 + **随机设备号** | `success` | **4600 → 4700** ★ 真加 100 |
    | 账号2 + 另一个随机号 | `success` | 4700（同天不再加） |
    | 账号1 + 原设备号 | `success` | 3750（今天已领，不变） |
    | 账号1 + 随机号 | `success` | 3750（不变） |

    → **换设备号后账号2 真的拿到了 100 分**。
  - **两个独立的 bug**：
    1. **程序跳过 claim**（主因）。`DailyCheckin` 的前置检查看到
       `did_checked_in=true` 就直接返回「已签到」，**连 claim 都不发** ——
       而实测存在「`did_checked_in=true` 但当天没领到额度」的状态
       （该账号 `checked_in=false`、无今日签到包）。因为跳过了 claim，
       程序**永远不会发现**换设备号就能救回来。
       → 修复：**无论前置状态如何，都发一次 claim**。
       已领时上游返 9095（幂等无副作用）；被误标但未领时会真正入账。
    2. **9095 后未尝试换设备号**。实测 9095 是**设备维度**的拒绝
       （"这个设备号今天签过"），而额度发放是**账号维度**的。
       → 修复：收到 9095 后**自动用新生成的 16 位设备号重试一次**，
       并以「额度是否真的增加」判定成败（不看 `code==0`，因为它可能是假成功）。
  - **纠正此前的多次误判**：去重粒度的最终结论是「**9095 按设备号判定，
    额度按账号发放**」——
    - v0.6.0 判"设备级" ❌
    - v0.6.1 判"账号+设备级" ❌
    - v0.6.3 判"账号级" ❌
    - **v0.6.6（正确）**：9095 的**拒签依据是设备号**，但**额度归属是账号**；
      所以换设备号能突破拒签并拿到该账号当天的额度
    - 之所以前几次全错：前两次实验时账号**没有**被设备标记，测不出差异；
      这次账号处于"被标记但未领到"的状态，才暴露了真实规则
  - 新增 `randDeviceID()`、`claimWithRotatedDevice()`
  - 测试更新：`TestDailyCheckinStillClaimsWhenMarkedCheckedIn`
    （前置已标已签时**仍应**发 claim）
  - **即时效果**：账号 `2222575719809915` 的额度已从 4600 增至 **4700**

### v0.6.5（2026-10-01）
- **修复对账误报：月初发放的 500 分包被当成了签到到账**
  - **用户反馈**：「昨天一个 93 的帐号，签到加 100，月初加 500，现在正好 693，
    昨天 4600 的帐号今天一点也没加」
  - **核对完全属实**：
    | 账号 | 额度 | 今日新建包 |
    |---|---|---|
    | 25311775596 | 92.8 → **692.8** ✅ | `500@00:00:00` + `100@11:54:57` |
    | 31444337795 | 4600 → 4600 ❌ | 仅 `500@00:00:00` |

    第一个账号正好是 `92.8 + 500（月初）+ 100（签到）= 692.8`，算术吻合。
  - **程序 bug（根因）**：v0.6.3 的对账逻辑把"今天的任意新包"都算作签到到账。
    每月 1 日上游会自动发**月度包**（实测 `limit=500 @00:00:00`），
    它的 `start_time` 也落在今天 —— 于是被误算成"签到到账 500"，
    并显示成"积分已在早先签到到账"，而实际该账号当天一分未加。
  - **修复**：`CurrentDayGrant()` 改为按两个特征识别真正的签到包
    1. **时间窗**：排除凌晨整点的定时发放（`hour < 1`）——月初包恰为 00:00:00
    2. **金额上限**：签到包是小额（实测 100/150），阈值 300；
       月度订阅包是 4000/500 这类大额，不计入
  - 日志会打印被排除的非签到包，便于核对：
    `今日无签到包（已排除非签到发放: [500@00:00:00(定时)]）`
  - **签到提示语改为据实播报**（不再一律说"已在早先签到到账"）：
    | 对账结果 | 提示 |
    |---|---|
    | 查到签到包 | 今日已签到（今日已到账 N 积分） |
    | 未查到签到包 | 今日已签到，但未查到新增积分（今日额度未增加） |
    | 对账本身失败 | 今日已签到（未能确认到账情况） |
  - 新增 2 个测试：`TestCurrentDayGrantIgnoresMonthlyPack`（月初包不算签到）、
    `TestCurrentDayGrantCountsOnlyCheckinPack`（月初包与签到包并存时只计签到包）
  - **用真实数据验证**：修复后的判定对两个账号分别给出
    「签到已到账 100」与「无签到到账」，与实际完全一致
  - **追查中的另一个发现**：账号2 在今天签到**之前** `did_checked_in` 就已经是
    `true`（日志 11:54:57 显示前置查询即为 true），所以程序连 `claim` 都没发。
    即上游对该账号预置了"已签"状态。这一现象**尚无定论**（可能与它是新号、
    `consumed=0`、额度较高有关），程序已能如实反映"标记已签但未到账"。

### v0.6.3（2026-09-30）
- **修复「提示签到成功但积分没涨」的最后一块** —— 增加签到后对账
  - **用户的决定性反馈**：「之前 4500 分的帐号提示签到成功现在 4600 分了，
    之前 93 分的帐号也提示签到成功但还是 93 分」
    → 一个真的加了 100，一个完全没加，**但两个都提示"成功"**。
  - **用权益包 start_time 逐一对账**（最硬的判据）：
    | 账号 | 额度变化 | 今日新建包 |
    |---|---|---|
    | 2222575719809915 | 4500 → **4600** ✅ | `limit=100 @07:03:09` |
    | 1554031214073648 | 4050 → 4050 ❌ | **无** |

    完全印证用户观察：账号1 被标记为已签，却**从未发放额度包**。
  - **根因（诚实说明）**：这是我的操作造成的。今天 07:03 我做设备号验证实验时
    对账号1 发过 `claim`，那次**用掉了它的今日签到名额，但额度包没有生成**，
    于是账号1 卡在"已标记签到但无包"的状态，当天再也签不了。**明天自动恢复。**
  - **真实缺口**：程序只看 `did_checked_in`（签到**标记**），
    无法察觉"标记成功但额度没到账"。若只看标记，就会把这种异常报成"签到成功"。
  - **修复**：新增 `CurrentDayGrant()` —— 查权益包里有没有
    `start_time` 落在**今天**的 credits 包。这是"额度真的到账"的唯一硬凭证。
    - `CheckinResult` 新增 `GrantMissing` 字段
    - 签到后自动对账：若标记已签但今日查无新包 → 提示改为
      **「已签到，但今日未查到新增额度（积分未增加）」**，不再谎报成功
    - 「全部签到」新增该分类的汇总
  - 新增 2 个测试：`TestCurrentDayGrantDetectsTodayPack`
    （只算今天的包，不把前天的算进来）、
    `TestCurrentDayGrantMissingWhenNoTodayPack`
  - **顺带纠正 v0.6.1 的结论**：去重粒度最终确认为 **账号级**
    - 矩阵实验（每格都换设备号）：

      | 账号 | 真实号 | 随机 A | 随机 B |
      |---|---|---|---|
      | 账号1（已签） | 9095 | 9095 | 9074 |
      | 账号2（未签） | success | success | success |

    而非"无法判断"——此前会跳过该包导致余额虚低。真实响应里最新签到包正是此形态。
  - 用**真实抓包响应**新增 4 个测试（`real_response_test.go`），锁定该口径。

### v0.5.2（2026-09-29）
- **修复 TraeWork 积分仍不正确（显示 150）**：v0.5.1 在权益包解析不出余额时，回退读取签到接口的 `credits` 字段，并假定其语义是「当前可用积分」——**该假定是错的**
  - 实测证据：该字段在 16 次采样中**恒为 150**，不随天数与消耗变化（对照 WorkBuddy 的余额有 2100/2200/2300/2400/2500 五种取值）；它是**签到奖励固定值**，不是余额
  - 用固定值冒充余额比报错更糟：会让「优先积分」策略把该账号当成恒定满额，影响选号
  - 现在**只认权益包里的真实余额**；解析不出即返回错误，面板显示「积分不可用」，并给出明确日志
  - 收紧了字段名白名单：移除裸 `credits` / `total` / `quota` 等宽泛名，避免误匹配到签到奖励值等无关字段
  - 解析失败时新增 `balance-candidates` 日志，打印权益包内**全部数值型字段的路径与值**，一次刷新即可确认真实字段名
  - 新增 5 个回归用例：禁止回退签到接口、忽略裸 `credits`、忽略裸 `credits/used` 减法、部分包不可解析时跳过

### v0.5.1（2026-09-29）

## 它解决什么问题

- WorkBuddy/CodeBuddy 和 TraeWork 账号的对话额度有限，多个账号可以共享/轮流使用
- 本项目把多个账号聚合成一个 **OpenAI 兼容 API**，按可选的策略（优先积分 / 优先过期 / 负载均衡）挑选账号、自动刷新 token、错误自动冷却
- 每天**自动签到**领额度，面板随时看积分、签到状态
- 全部在一个后台托盘程序里，无需任何编程环境

## 快速开始（普通用户）

1. **下载**：从 [Releases](https://github.com/sddvcm/workbuddy-wild/releases) 下载最新版 `workbuddy-wild-windows-amd64.zip`，解压后双击 `workbuddy-wild.exe`
2. 稍等片刻会弹出提示框，显示 **OpenAI 兼容 API 地址**（默认 `http://127.0.0.1:7863`）——记住它，关掉即可
3. 右下角出现绿色 W 托盘图标，**单击 / 双击 / 右击** 都能打开管理面板
4. **添加账号**：面板点"＋ 添加账号"→ 选择 WorkBuddy 或 TraeWork → 自动打开无痕浏览器 → 登录对应平台 → 自动写入凭证并立即签到
5. **配置客户端**：把你的 AI 客户端指向
   ```
   Base URL: http://127.0.0.1:7863/v1
   API Key:  WorkBuddy2API   （面板"API-Key"处可随时修改）
   ```
6. 面板里还能：改自动签到时间（默认每天 09:00、21:00，支持分钟）、看签到状态、刷新积分、改监听地址、开机自启、查看日志、退出

> 首次运行自动生成 `config.json`（默认监听 `127.0.0.1:7863`）。程序常驻托盘，双击 exe 只是唤起/提示，主界面通过托盘图标打开。

## 与原始项目的区别

| | 原始 workbuddy2api | WorkBuddy Wild |
|---|---|---|
| 使用方式 | 命令行 + 脚本 + Docker，需安装 Go/Python/Docker | **单个 exe 双击即用**，零依赖 |
| 界面 | 无（纯 HTTP 服务） | **系统托盘管理面板**（添加账号/签到/积分/配置） |
| 登录 | Bash 脚本 + 手动复制粘贴授权 URL | 一键拉起**无痕浏览器**，自动完成登录轮询 |
| 签到 | 手动跑脚本 / 固定 9·21 点 | 面板**可视配置签到时间（支持分钟）**，即时生效 |
| 账号状态 | 无 | 面板实时展示**积分/签到记录/冷却状态**，单账号手动签到/刷新 |
| 监听配置 | 改配置文件重启 | 面板下拉选择 + **热切换**（不重启） |
| 日志 | 控制台 | 写 `data/app.log`，面板一键记事本打开 |
| 构建 | Linux 优先 | Windows 单文件，GitHub Actions 自动发布 |

## 客户端兼容性（pi / Claude Code 等）

兼容标准 OpenAI 格式（`/v1/chat/completions`）。特别的兼容处理：

- **模型 ID 必须带平台前缀**：`workbuddy/<model>` 或 `traework/<model>`。
  例如 `workbuddy/hy3`、`workbuddy/deepseek-v4-pro`、`traework/DeepSeek-V4-Flash`。
  不带前缀的模型名会返回 400 错误。
- **`developer` 角色自动转换**：pi 等客户端对推理模型会用 `role=developer` 发送系统提示词。
  两条上游管道均已自动将 `developer` 归一化为 `system`，避免内容过滤误杀。

### 获取完整模型列表

所有可用模型通过标准 OpenAI `/v1/models` 端点获取，直接请求：

```bash
curl http://127.0.0.1:7863/v1/models -H "Authorization: Bearer WorkBuddy2API"
```

返回的列表中每模型都带 `workbuddy/` 或 `traework/` 前缀。
可以让 agent 先拉取模型列表，再依据下面的配置示例自动生成 models.json。

### pi 配置示例

编辑 `C:\Users\<用户名>\.pi\agent\models.json`，在 `providers` 中加入：

```jsonc
"workbuddy-wild": {
  "name": "WorkBuddy-Wild",
  "api": "openai-completions",
  "baseUrl": "http://127.0.0.1:7863/v1",
  "apiKey": "WorkBuddy2API",
  "models": [
    {
      "id": "workbuddy/hy3",
      "name": "hy3 (WorkBuddy)",
      "reasoning": true,
      "input": ["text"],
      "contextWindow": 192000,
      "maxTokens": 64000,
      "compat": { "maxTokensField": "max_tokens" }
    },
    {
      "id": "traework/DeepSeek-V4-Flash",
      "name": "DeepSeek V4 Flash (TraeWork)",
      "reasoning": true,
      "input": ["text"],
      "contextWindow": 1000000,
      "maxTokens": 50000,
      "compat": {
        "thinkingFormat": "deepseek",
        "supportsReasoningEffort": true,
        "maxTokensField": "max_tokens"
      }
    }
  ]
}
```

> 模型 ID 必须按 `workbuddy/` 或 `traework/` 前缀，否则请求被拒。
> 名称建议标注来源 `(WorkBuddy)` / `(TraeWork)` 以便区分同名模型。
> 建议只配置实际要用的模型，避免列表过长。

## 常见问题

**提示框显示的地址访问不了？**
检查是否改过监听地址：面板"API 监听"里看当前地址；或看 `data\app.log`（面板"查看日志"）。

**添加账号时浏览器没打开？**
面板登录框里有"复制链接"，可手动在浏览器（无痕窗口）打开完成登录。

**签到时间改了没生效？**
时间修改即写回 `config.json` 并立即生效，无需重启。

**Windows 提示“未知发布者”或报毒？**

本工具没有数字签名，因此可能会被 Windows 安全中心或杀毒软件拦截。如果报毒，请将本工具添加到排除项：

设置 → 更新和安全 → Windows 安全中心 → 打开 Windows 安全中心 → 病毒和威胁防护 → “病毒和威胁防护”设置/管理设置 → 排除项/添加或删除排除项 → 添加排除项（文件或文件夹），把 exe 或所在目录加进去。

如果对本仓库发布包不放心，可以自行基于源码构建（见开发文档）。

**TraeWork 多账号自动签到失败**

TraeWork有风控机制，无法确保多账号能可靠自动签到，这种情况建议使用客户端手动签到，登出客户端重新用另一账号登录即可签到。本工具的 API 转换功能不受影响。
